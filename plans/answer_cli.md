# Plan: `llmgrader_answer` — have a model sit the course's own questions

A new console script that asks an LLM to answer a unit's questions from the
**question text alone** — no solution, no rubric, no grading notes — and writes
the answers out as a `<unit_test>` file that `llmgrader_test run` then grades.

```
llmgrader_answer example_repo/unit1/calculus.xml --out ai_answers.xml
llmgrader_test run ai_answers.xml --html ai_report.html
```

## Motivation

The obvious reading is curiosity: how well do these models do on the course's
problems? That is real, but two byproducts are worth more.

**It is a rubric stress test.** When a strong model answers a question blind and
scores 3/10, the usual cause is not that the model is weak. It is that the
question is under-specified, or that a rubric item keys on phrasing rather than
substance. You cannot get that signal from your own hand-written cases, because
you write those already knowing what the rubric wants. A blind answer is the
closest thing available to a naive competent student.

**It seeds grading tests.** The cases that are tedious to author are the "good
but not perfect" ones — the near-misses that decide whether a rubric is tuned.
Those are exactly what a model produces unprompted. The output file is designed
to be *edited into* a real test file: the instructor reads each answer, types a
band, and keeps it. That is why the output is `unit_test.xsd` rather than a
bespoke report format.

Neither justifies much complexity, so this is deliberately a small tool that
borrows nearly everything from `gradetests.py`.

## What already exists

Almost all of it. The new code is one model call and one XML emitter.

| Need | Already in the tree |
| --- | --- |
| Load full question dicts from a loose unit file | `synthesize_package()` + `Grader(...)`, exactly as `_plan_run` does (`gradetests.py:1897`) |
| Load them from a built package | `PackageContext` |
| Per-question model choice | `preferred_model_for()`, `resolve_preferred_model()`, `DEFAULT_MODEL_SIMPLE` |
| Concurrency | the `ThreadPoolExecutor` block in `_execute_run` |
| Cost estimate and its caveat | `price_call()`, `LONG_CONTEXT_CAVEAT` |
| Image resolution to data URIs | `UnitParser._extract_solution_images()` |
| Self-check the emitted file | `validate_test_file()`, `check_file()` |
| CLI conventions | `scripts/llmgrader_test.py` in full |

Two things that look reusable and are not:

- **`gradetests.load_unit()` is insufficient.** It reads only what a *check*
  needs — `partial_credit`, `parts`, `rubric_items`, `rubric_groups` — and
  deliberately drops `question_text`. Answering needs the question. Go through
  `synthesize_package()` + `Grader` like `_plan_run`, which yields the complete
  question dict from `UnitParser.parse()`.
- **`_make_openai_caller()` cannot be reused.** It pins
  `text.format = {"type": "json_object"}` and parses the reply into
  `GraderRawResult`. Answering wants free-form prose. Write a sibling in the new
  module; keep its `spec.supports_temperature` gate, since the GPT-5.6 family
  rejects `temperature` outright and the key must be absent rather than set.

## Design decisions

### 1. The output is a `<unit_test>` file, assertion-free by default

`unit_test.xsd` already permits this: `expected_points`, `expected_result` and
`expected_rubrics` are all `minOccurs="0"`, and `check_file` treats an
assertion-less case as a **warning**, not an error (`gradetests.py:539`). So a
generated file passes `llmgrader_test check` and is accepted by `run`.

```xml
<unit_test unit="../calculus.xml">
  <!-- Generated by llmgrader_answer on 2026-09-11.
       Each answer was produced from the question text alone:
       no solution, no rubric, no grading notes. -->
  <case id="ai_exponential_derivative_1" qtag="Exponential derivative">
    <description>gpt-5.6 answered this from the question text alone (attempt 1 of 3).</description>
    <solution><![CDATA[ ... ]]></solution>
  </case>
</unit_test>
```

`caseType` is a closed `xs:all` carrying only `id` and `qtag`, so there is
nowhere to hang a `model=` attribute. **Provenance goes in `<description>` and
in XML comments** — that is the only place it fits, and `description` is
required anyway.

Case ids must be deterministic and derived from a slugified qtag, so that
re-running the tool produces a readable diff rather than a reshuffle.

### 2. `--expect full` makes the run report read as a score

With no assertions, `llmgrader_test run` grades every case and then reports
`pass` for all of them, because there is nothing to violate. The points are
visible in the score column, but the verdict column is noise.

`--expect full` (off by default) emits a full-credit assertion instead:

- binary question → `<expected_result>pass</expected_result>`
- partial-credit question → one `<part label="X" min="{that part's points}"/>`
  per part, no `max`

Then the summary line reads directly as "the model got N of M right", which is
the curiosity payoff. `<parts>` is `minOccurs="1"` in `unit.xsd`, so a real
label always exists. A `min = part total` band with no `max` trips none of
`_check_case_against_question`'s findings: the "spans the whole range" warning
needs `min <= 0`, and the "max above the part total" error needs a `max`.

Default is off because the generated file's primary destiny is to be edited
into real cases, and a wrong assertion is worse than no assertion.

### 3. The prompt gets the question and nothing else

This is the property the whole tool rests on. The assembled prompt contains
`question_text`, the part labels with their point values, and question images.
It must never contain `solution`, `solution_images`, `grading_notes`,
`rubrics`, or `rubric_total`. The moment the rubric leaks, the exercise stops
measuring anything. There is a test for this, and it is the most important
test in the suite.

Part labels are included for a mundane reason: the grader scores per part, and
an answer that silently skips part (b) loses those points for a reason that is
not about the model's ability. Tell the model the labels and the points and ask
for an answer labelled by part.

### 4. Temperature 0 where the model allows it

Reproducibility matters more than variety here — `--repeat` exists to expose
instability, and it is more informative when the *only* source of variation is
the provider's own nondeterminism rather than a temperature setting. Reuse the
`spec.supports_temperature` gate verbatim.

## Caveats — the real work

### 1. Question images

If `question_text` embeds an `img` tag, a text-only prompt asks the model to
solve a problem it cannot see, and the resulting score means nothing at all.

`UnitParser._extract_solution_images(html, soln_pkg_path, xml_path, log)`
already does HTML → data-URI resolution for solutions; point it at the question
text and attach the results as `input_image` content parts, the way
`_build_message_content` does.

Under a package synthesized from a loose unit file, those paths may not
resolve. `llmgrader_test run` treats the equivalent situation as **fatal**
(`gradetests.py:1927`, "grading without them would test something other than
what students hit"). Here a hard failure is too strong — an image-free unit is
the common case and should just work — but an unresolved image must produce a
loud per-question warning naming `--pkg` as the fix, and the count must appear
in the final summary. Silence here produces a plausible-looking number that is
worthless.

### 2. Empty and refusing answers must survive

If the model returns nothing, or refuses, **emit the case anyway** and say so
in the `<description>`. Never drop it. A blank answer that goes on to score
well is the single most valuable thing this tool can surface — `gpt-4.1-mini`
has been observed awarding 10/10 to an empty submission. Dropping the case
would hide exactly the failure worth finding.

### 3. CDATA termination

Model output is arbitrary text and may contain the CDATA terminator. Split the
section rather than escaping, and test it.

### 4. `--out` clobbering

The output file is meant to be hand-edited afterwards. Refuse to overwrite an
existing file unless `--force`, or a second run silently destroys an evening of
band-writing.

## CLI

```
llmgrader_answer UNIT.xml [UNIT.xml ...]
                 [--pkg PATH] [--qtag TAG]... [--model ID|TIER]
                 [--repeat N] [--jobs N] [--timeout SEC]
                 [--out FILE] [--force] [--expect full]
                 [--dry-run] [--cost] [--api-key KEY] [-v] [-q]
```

Mirror `llmgrader_test` deliberately, down to the help-text voice: positional
paths, repeatable `--qtag`, `--model` accepting a tier name or a concrete id,
`--pkg` for a built solution package, `--dry-run` printing the call count and
per-model breakdown, `--cost` printing a registry-rate estimate with the same
caveat, `--api-key` falling back to `OPENAI_API_KEY`, exit codes 0/1/2 with the
same meanings.

- Unflagged, each question is answered by the model the course would *grade* it
  with: `preferred_model_for()` then `DEFAULT_MODEL_SIMPLE`. That makes the
  default run a fair-ish mirror of the course's own configuration.
- `--out` defaults to `<unit-stem>_answers.xml` beside the current directory.

## Module layout

Mirror the gradetests split exactly:

- `llmgrader/services/answers.py` — all logic. No printing, no argparse.
- `llmgrader/scripts/llmgrader_answer.py` — argparse, terminal table, exit code.
- one line in `[project.scripts]` in `pyproject.toml`.

## Out of scope

- Grading the answers. That is `llmgrader_test run`, already built.
- Any non-OpenAI provider. `PROVIDER_CALLERS` has one entry today; follow it.
- Persisting results to the submissions DB. The XML file is the artifact.
- Any change to the student-facing grading path.
