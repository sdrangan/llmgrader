# Having a Model Answer Your Questions

## Overview

`llmgrader_answer` asks a model to answer your unit's questions from the
**question text alone** — no solution, no rubric, no grading notes — and writes
the answers out as a `<unit_test>` file. `llmgrader_test run` then grades them
the way it grades any other test file.

```bash
llmgrader_answer unit1/calculus.xml --out unit1/tests/ai_answers.xml
llmgrader_test run unit1/tests/ai_answers.xml --html ai_report.html
```

The obvious reading is curiosity: how well does the model do on your problems?
That is real, but it is the least useful of the three things this gives you.

**It is a rubric stress test — the main reason to run it.** When a strong model
answers a question blind and scores 3 out of 10, the usual cause is not that
the model is weak. It is that the question is under-specified, or that a rubric
item keys on phrasing rather than on substance. You cannot get that signal from
your own hand-written test cases, because you write those already knowing what
the rubric wants. A blind answer is the closest thing available to a naive
competent student.

**It seeds grading tests.** The cases that are tedious to author are the "good
but not perfect" ones — the near-misses that decide whether a rubric is tuned.
Those are exactly what a model produces unprompted. The output file is designed
to be *edited into* a real test file: read each answer, decide what it is
worth, type the band in, and keep it. That is why the output is a
`<unit_test>` file and not a report format of its own.

**And then it tells you how the model did**, which is the part you were curious
about.

## What a low score means

Read this before you read a number this tool produces.

A low score is **first** evidence about your question and your rubric, and only
**second** evidence about the model. That ordering is not politeness; it is
what the tool is for.

Concretely, when a case scores badly, the causes worth checking, in order:

1. **The question does not ask for what the rubric rewards.** A rubric item for
   "states the limit as x → ∞" against a question that says only "sketch the
   function" is asking for something the student was never told to provide.
   Every student loses that point, and you would never notice from your own
   test cases, because you wrote them knowing the item was there.
2. **A rubric item keys on phrasing.** "Student writes *u = x* and
   *dv = e^{2x} dx*" fails a student who chose the same substitution and named
   it differently. The grader is reading for the words, not the substance.
3. **The question embeds a figure the model could not see.** See
   [Questions with images](#questions-with-images) below. If the summary
   reported unresolved images, stop here — that score means nothing.
4. **The model genuinely could not do the problem.** This happens, and it is
   worth knowing. It is the last thing to conclude, not the first.

An instructor who runs this once and reads the score as a verdict on the AI has
got the wrong artifact out of it. The right artifact is the list of rubric
items that a correct-looking answer failed to earn.

## The two-step workflow

### Step 1 — generate the answers

```bash
# See what it would cost first. Free.
llmgrader_answer unit1/calculus.xml --dry-run --cost

# Then generate.
llmgrader_answer unit1/calculus.xml --out unit1/tests/ai_answers.xml
```

Each question is answered by the model your course would *grade* it with — its
own `preferred_model`, falling back to the `simple` tier default — so an
unflagged run mirrors your own configuration. `--model` overrides that for
every question, with a tier name or a concrete id.

The generated file looks like this:

```xml
<unit_test unit="../calculus.xml">

  <!--
    Generated by llmgrader_answer on 2026-09-11 from calculus.xml.

    Every answer below was produced from the question text alone: no
    solution, no rubric, no grading notes. ...
  -->

  <case id="ai_exponential_derivative_1" qtag="Exponential derivative">
    <description>gpt-5.6-luna answered this from the question text alone: no solution, no rubric, no grading notes.</description>
    <solution><![CDATA[ ... the model's answer ... ]]></solution>
  </case>

</unit_test>
```

Case ids are derived from the qtag and are stable, so re-running the tool
produces a readable diff rather than a reshuffle. The `ai_` prefix marks a
generated case in a file that ends up holding both kinds.

By default the cases **assert nothing**. `llmgrader_test check` reports that as
one warning per case, which is correct and expected: the file is not a set of
grading tests yet. It becomes one when you write the bands in.

### Step 2 — grade them

```bash
llmgrader_test run unit1/tests/ai_answers.xml --html ai_report.html
```

Then open the HTML report and read the grader's evidence for each rubric item.
That is where the rubric problems are visible — not in the score column.

### Step 3 — keep the good ones

For each answer worth keeping, replace nothing and add the assertion you
believe is right:

```xml
  <case id="ai_integration_by_parts_1" qtag="Integration by parts">
    <description>...</description>
    <solution><![CDATA[ ... ]]></solution>

    <!-- Added by hand: the setup is right, the limits were never applied. -->
    <expected_points>
      <part label="all" min="4" max="8"/>
    </expected_points>
    <expected_rubrics>
      <item id="apply_limits" min="0" max="0"/>
    </expected_rubrics>
  </case>
```

Delete the cases you do not want and rewrite the descriptions in your own
words. What you are left with is an ordinary grading test file — see
[Testing your grading](./gradetests.md) for what the assertions mean.

Because the file is meant to be edited, **`llmgrader_answer` refuses to
overwrite an existing output file** unless you pass `--force`. A second run
that silently replaced it would destroy an evening of band-writing.

## `--expect full`: read the run as a score

If what you want *is* the number, `--expect full` writes a full-credit
assertion into every case:

```bash
llmgrader_answer unit1/calculus.xml --expect full --out ai_answers.xml
llmgrader_test run ai_answers.xml
```

A binary question gets `<expected_result>pass</expected_result>`; a
partial-credit question gets a `min` equal to each part's point total and no
`max`. Then the run's summary line reads directly as "the model got N of M
right".

It is off by default because the generated file's primary destiny is to be
edited into real cases, and a wrong assertion is worse than no assertion.

## Questions with images

This is the caveat that matters most, because it is the one that produces a
plausible-looking number that is worthless.

If a question's text embeds an `<img>` tag, the model has to see the figure to
answer. `llmgrader_answer` resolves those images and attaches them to the call
— but a `/pkg_assets/...` source only resolves inside a **built solution
package**, and a run over a loose unit file may not find it.

When that happens the tool says so, per question, and counts it in the summary:

```
  warning: 'Exponential graphing' has 1 question image(s) that did not
  resolve; the model answers without seeing them.
  Build a solution package and pass --pkg to fix this.
```

The warning is also written into that case's `<description>`, so it survives
into the file and into the grading report.

The fix is to build the package and point at it:

```bash
create_soln_pkg          # produces soln_package/ and soln_package.zip
llmgrader_answer unit1/calculus.xml --pkg soln_package.zip --out ai_answers.xml
```

An **image-free unit needs none of this** and works from the loose unit file,
which is why an unresolved image is a warning here rather than the hard error
`llmgrader_test run` raises for the same situation.

## Empty and refusing answers are kept

If the model returns nothing, or declines to answer, the case is written out
anyway with a note in its `<description>`. It is never dropped.

This is deliberate. A blank submission that goes on to score well is the single
most valuable thing this tool can surface — `gpt-4.1-mini` has been observed
awarding 10 out of 10 to an empty answer. Dropping the case would hide exactly
the failure worth finding.

A call that *fails* — a timeout, a network error, an expired key — is different:
there is no answer, so no case is invented for it. The failure is named in the
summary and the command exits `1`.

## Options

```
llmgrader_answer UNIT.xml [UNIT.xml ...]
                 [--pkg PATH] [--qtag TAG]... [--model ID|TIER]
                 [--repeat N] [--jobs N] [--timeout SEC]
                 [--out FILE] [--force] [--expect full]
                 [--dry-run] [--cost] [--api-key KEY] [-v] [-q]
```

```bash
# What would this cost? Free, makes no calls.
llmgrader_answer unit1/calculus.xml --dry-run --cost

# One question only
llmgrader_answer unit1/calculus.xml --qtag "Exponential derivative"

# Three independent attempts at each question, as three cases
llmgrader_answer unit1/calculus.xml --repeat 3

# Would a stronger model do better? If not, suspect the question.
llmgrader_answer unit1/calculus.xml --model complex

# Read the answers from a built package, so question images resolve
llmgrader_answer unit1/calculus.xml --pkg soln_package.zip
```

`--out` names one file and a `<unit_test>` file targets one unit, so a run over
several units must leave `--out` off; each unit then gets
`<unit-stem>_answers.xml` in the current directory.

`--repeat` is worth using on a question you suspect is ambiguous. Three answers
that differ in what they cover, all scoring differently, is a question that
does not say what it wants.

Answers are generated with `temperature 0` where the model allows it, so
`--repeat` exposes the provider's own nondeterminism rather than variation you
asked for.

Exit codes: `0` every question was answered and the file was written, `1` at
least one call failed, `2` the run could not be performed at all — a missing
unit, a `--qtag` that matched nothing, no API key, or an output file that
already exists without `--force`.

## What this does not do

- **It does not grade.** That is `llmgrader_test run`, which already exists.
- **It does not know whether an answer is right.** It only records what the
  model said. The verdict comes from your rubric, which is the point.
- **It is not a benchmark.** One run over one unit with one model is a
  conversation starter about your rubric, not a measurement of anything.
