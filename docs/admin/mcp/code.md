# Publishing Demo Code and Docs

A lot of what a course teaches lives in its demos, not its slides: the slides
say "the IP gets an AXI4-Lite register interface", and the demo's source shows
the five `#pragma HLS INTERFACE s_axilite` lines that do it. With demo code
published, a student's assistant can answer "where is this shown?" and "how do
I write this?" from your own demos and the docs pages that walk through them,
and give the student a link to the exact lines.

The demos must be in a **public GitHub repository**. The portal keeps its own
copy of the parts you choose and follows the branch: push a fix and students
see it within ten minutes, **without rebuilding or uploading the course
package**. Only a pointer to the repository goes in the package.

---

## What students get

Four tools, beside the slide tools:

| Tool | What it does |
| --- | --- |
| `list_demos` | Every demo: its title and description, its docs pages, its code, and the slides and unit it goes with |
| `list_demo_files` | One demo's files: docs pages first, in reading order, then code |
| `get_demo_file` | A docs page or source file with line numbers, 400 lines at a time |
| `search_demos` | A literal, case-insensitive search for an identifier or phrase (`s_axilite`, `always_ff`) across code and docs |

Every result links somewhere a student can open: a docs page to its published
page on your docs site, and code to the exact lines on GitHub, pinned to the
commit the portal is serving so the line numbers are always right.
`get_slide` and `search_slides` also say which demos a slide cites.

---

## Step 1: Point the package at the repository

Add a `<code>` element to `llmgrader_mcp_config.xml`, after any `<unit_types>`:

```xml
<code repo="https://github.com/sdrangan/hwdesign" branch="main" root="pub">
  <include path="demos"/>
  <include path="docs/demos" kind="doc"/>
  <exclude>*.wcfg</exclude>
</code>
```

| Part | Meaning |
| --- | --- |
| `repo` | The public GitHub repository. Only `https://github.com/<owner>/<repo>` is accepted. |
| `branch` | The branch to follow. Default `main`. |
| `<include path>` | A folder of the repository to publish. Nothing outside the included folders is fetched or served. |
| `kind="doc"` | The folder holds Markdown docs pages: only its `.md` files are served. Default `code`. |
| `<exclude>` | A glob to leave out, relative to the repository root (`demos/project/**`), or a file-name glob (`*.wcfg`). |
| `root` | Optional: a `<root>` that holds your local checkout of the repository, for the link check in step 3. |
| `site` | Optional: where the docs are published. By default it is read from the repository's `_config.yml` (`url` + `baseurl`), as GitHub Pages uses. |
| `links` | Optional: the overrides file (step 4). Default `demos/demos.xml`. |

**What is never served**, whatever you include: build output (`hls_component/`,
`.Xil/`, `logs/`, `*_proj/`, `*.runs/` and the like), bitstreams and other
binaries, Tcl that Vivado generated (`Generated by Vivado` in its header),
files over 256 KB, docs images, and symbolic links. Notebooks are served with
their outputs removed.

---

## Step 2: Turn it on

On Render, add the environment variable:

| Variable | Value | Remarks |
| --- | --- | --- |
| `LLMGRADER_MCP_CODE` | `1` | Serves the demo tools. Off when unset: delete it to turn them off. |
| `LLMGRADER_CODE_SYNC_TTL_S` | seconds | Optional. How old the copy may get before it is refreshed. Default `600`. |

Then rebuild the package (`create_soln_pkg`) and upload it as usual. The first
MCP request after that clones the repository in the background, which takes a
few seconds; a demo question asked in those seconds is told to try again in a
minute.

The copy lives under `<storage>/courses/<course_id>/code/`. It is checked
against GitHub at most every ten minutes, never while a student waits: a call
is always answered from the copy in hand, and if GitHub cannot be reached, the
last good copy keeps being served.

---

## Step 3: Check the links

The portal works out on its own which demo is which, and which slides and unit
go with it, from references your slides and docs pages already make:

- **A demo** is a folder of docs pages (`docs/demos/procif/`), with the code
  its pages cite -- *"the files are in `hwdesign/demos/scalar_fun/scalar_fun_vitis`"*
  -- and the code folder of the same name. Its title and description come from
  the folder's `index.md`.
- **A code folder no docs page cites** (`demos/fsm`) is a demo of its own,
  described by its README if it has one.
- **A slide that cites a demo** -- a path such as `demos/stream/avgfilt` in its
  text or notes, a GitHub link, or a link to a docs page, written out or as a
  hyperlink -- ties the demo to that slide and, through its deck, to a unit.
  A deck with the same name as a demo gives the demo its unit.

With `root=` set, see what that produces before you upload:

```bash
llmgrader_mcp_build --links
```

It reads your local checkout (tracked files only) and the slides already built
into `soln_package/`, and prints each demo with its docs, code, slides and
unit, then everything worth fixing:

```text
Demos with no unit (add a slide link, or <unit> in the overrides file): datatypes, conv2d
Broken reference: docs/demos/simp_fun/poly.md:32 cites demos/basic_logic/poly_fun.sv, which does not exist
```

`create_soln_pkg` prints the same report. Nothing in it stops a build.

**The best fix is at the source.** A slide that says only
`sdrangan.github.io/hwdesign` ties nothing to anything; one that names the
demo's folder, or links to its docs page, ties the demo to that slide and its
unit automatically.

## Step 4 (optional): The overrides file

For what no slide or page says, add `demos/demos.xml` to the demo repository.
It is read on every sync, so a change needs no rebuild. It is checked against
`llmgrader_demos.xsd`; a broken one is refused and the previous copy stays in
service.

```xml
<demos>
  <!-- A unit, or slides, for a demo no slide cites. -->
  <demo id="datatypes"><slides deck="basic-logic" first="20" last="31"/></demo>
  <demo id="conv2d"><unit>Unit 10:  Arrays and Matrix Multiplication</unit></demo>

  <!-- A title and description for a demo with no docs page or README. -->
  <demo id="histogram" title="Histogram with HLS">
    <description>Building a histogram in Vitis HLS, and why its loop does not pipeline.</description>
  </demo>

  <!-- Drop a wrong automatic link to a deck. -->
  <demo id="sharedmem"><not_slides deck="sharedmem"/></demo>

  <!-- A folder that is not a demo.  Its files stay searchable. -->
  <hide id="project"/>
</demos>
```

`id` is the demo's id as `--links` lists it. A unit is written as its `<name>`
in `llmgrader_config.xml`, double spaces and all. An id or deck that matches
nothing is reported by `--links`.

## Checking and updating the served commit

**Admin ▸ Manage Courses** has a **Demo code** column. For each course that
publishes demo code it shows the commit the course MCP is serving, and a
status:

| Status | Meaning |
| --- | --- |
| Up to date | GitHub's branch head is the commit being served. |
| Update available | GitHub has a newer commit. Students get it within ten minutes anyway, or now with **Update now**. |
| Syncing… | A sync is running. |
| Error | The last sync or the last check of GitHub failed. The last good copy is still being served. |
| Not checked | GitHub has not been asked yet. |
| Not synced yet | No copy has been made. The first MCP request makes one. |

The column shows "—" for a course whose package has no `<code>`, and "off"
when `LLMGRADER_MCP_CODE` is not set. Opening Manage Courses asks GitHub for
the branch head of every course with demo code, so the column fills in by
itself within a few seconds.

Click the cell to open the course's **Demo code** dialog. It shows:

- the commit being served, with its date and message, and the branch head on
  GitHub, with how long ago it was checked. Each commit links to GitHub. When
  they differ, **See what changed on GitHub** opens the comparison, which is
  worth a look before updating;
- when the copy was last synced and, if the last sync failed, why, and which
  commit is still being served.

**Check again** asks GitHub for the branch head again. **Update now**, offered
when an update is available or the last sync failed, pulls the new commit in
at once rather than waiting for the next refresh. The dialog shows the sync's
stages as it goes (checking remote, fetching, building snapshot, validating),
then "Now serving" and the new commit. A sync with nothing new takes a second
or two; one that fetches takes a few seconds. If the new commit is refused
(say its overrides file does not validate), the dialog says so and the old
commit stays served.

Nothing in the dialog waits on GitHub: checking and updating run in the
background on the portal, and the dialog follows them. Grading carries on
throughout.

**With several gunicorn workers**, the sync runs in the worker that received
the click; a second worker cannot start one on top of it. The others pick up
the new commit on their next MCP request. So "Now serving" is true of the copy
on disk at once and of every worker after its next MCP call. Render runs one
worker, so there the two are the same.

## What is recorded

Demo calls are recorded like every other MCP call
([what is recorded](./deploy.md#what-is-recorded)): the demo and file asked
about and the commit that answered, never the search terms.
**Analytics ▸ MCP DB ▸ Demos: calls by demo and file** groups them.
